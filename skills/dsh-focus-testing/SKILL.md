# 让检查证明用户需要的行为

1. 先确认要证明的行为和最小有效检查。复用项目已有测试与运行方式；不要为了一个小改引入新的测试框架。界面交互用实际页面验证，纯计算和数据转换优先使用已有自动测试。
2. 任务包含产品缺陷时，首次修改实现前加载或沿用本版本「定位修复」（`dsh-focus-debugging`）。先让相关检查在旧实现上因该缺陷失败，再做最小修改使它通过；已有失败记录仍适用时直接复用。新增逻辑具备合适的测试环境时先写行为断言，再实现；环境缺失或命令找不到不算已复现产品缺陷。
3. 断言用户可观察的结果，按实际风险覆盖成功、错误输入和必要边界。测试不能只是重复实现代码，不能只断言模拟对象被调用，也不能通过删除失败断言或降低原要求制造通过。
4. 异步界面等待实际状态或条件出现，避免靠固定睡眠猜测时机。分清脚本定位错误、环境故障和产品缺陷；前两类不要靠改业务代码掩盖。
5. 直接运行检查命令并保留其退出码，包括预期失败的测试；不能用 `exit 0` 隐藏失败，也不要在测试后追加成功的打印语句来结束命令。确需打印状态时先保存退出码，最后用该状态退出，例如 `node --test tests.mjs; result=$?; printf '退出码：%s\n' "$result"; exit "$result"`。阅读真实输出，不能把“测试启动了”写成“测试通过”。修改后运行相关检查；失败原因不明时使用「定位修复」。
6. 相关检查通过且没有新增修改、失败或疑点时停止重复测试，回到当前计划。本次改动公开接口、数据校验、状态行为或多个模块时，交付前加载或沿用本版本「结果检查」（`dsh-focus-review`）中的代码检查方法，即使代码很短也要检查这些行为。说明实际验证范围，测试数据和模拟结果不能冒充真实服务或日常安装验收。
