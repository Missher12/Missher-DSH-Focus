# 先解释失败，再修改

遵循用户要求和当前项目约定，保留原任务目标及已有有效工作。

1. 从实际错误、失败命令或用户给出的现象出发。整理预期行为、实际行为和已知条件；已有日志和复现结果足够时直接使用。
2. 找出一条有证据支持的原因假设，选择能区分该假设与其他原因的最小检查。工具不可用、权限不足、依赖缺失时先解决该前提；不要把环境错误当成产品代码缺陷。
3. 相同操作因相同原因失败两次后，先解释已有证据，再调整方法。不要原样重试，也不要同时随机修改多个无关位置。若前提已经改变且有明确依据，可以重试，并说明变化。
4. 针对原因做最小且完整的修改。涉及行为回归时加载「针对性测试」（`dsh-focus-testing`），先确认旧实现确实失败，再验证修复。简单文案和外观调整不另建测试体系。
5. 辅助记录工具报参数或结构错误时，按当前工具定义修正，不能反复猜参数。如果该记录并非完成用户目标的前提，继续可用的真实验证并说明记录未生成；若用户目标确实依赖该工具，就保留未完成状态，不伪造回执或绕过必要要求。
6. 修复后回到原任务的未完成项。独立修复任务完成后按改动规模进行「代码检查」（`dsh-focus-review`），再交付。无法继续时说明具体卡点、已经验证的事实以及真正缺少的信息，不假装修好。

执行增强会在首次失败时提示检查原因，同一调用同一失败达到两次时加强提醒。预期的失败测试不是新的事故；读取本技能后已有提醒会消除，新的失败仍会提示。提醒不会代替实际错误证据或强制停止工具。
