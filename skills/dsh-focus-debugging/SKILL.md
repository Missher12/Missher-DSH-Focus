# 先解释失败，再修改

遵循用户要求和当前项目约定，保留原任务目标及已有有效工作。

1. 从实际错误、原始材料或用户给出的现象出发，区分预期结果、实际结果和已知条件。已有记录足够时直接使用，不为证明失败重复操作。
2. 找出有证据支持的原因假设，用最小必要检查区分原因。材料冲突先比较日期、版本、范围和统计口径；查不到或无法判断时保留未知，不拼凑结论。工具、权限或依赖缺失时处理相应前提，不把环境问题当成内容或代码缺陷。
3. 相同操作因相同原因失败两次后，先解释已有证据，再调整方法。不要原样重试，也不要同时随机修改多个无关位置。若前提已经改变且有明确依据，可以重试，并说明变化。
4. 针对原因做最小且完整的修正。代码行为回归时加载「针对性测试」（`dsh-focus-testing`）；一般事务使用原始来源、计算结果或实际操作状态核对，不为此搭建测试体系。发送、付款等操作状态不明确时先查已有结果，避免重复执行；这不增加原有授权。
5. 辅助记录工具报参数或结构错误时，按当前工具定义修正，不能反复猜参数。如果该记录并非完成用户目标的前提，继续可用的真实验证并说明记录未生成；若用户目标确实依赖该工具，就保留未完成状态，不伪造回执或绕过必要要求。
6. 处理后回到原任务的未完成项，按影响范围进行「结果检查」（`dsh-focus-review`）后交付。无法继续时说明具体卡点、已验证事实和真正缺少的信息，不假装完成。

执行增强会在首次失败时提示检查原因，同一调用同一失败达到两次时加强提醒。预期的失败测试不是新的事故；读取本技能后已有提醒会消除，新的失败仍会提示。提醒不会代替实际错误证据或强制停止工具。
