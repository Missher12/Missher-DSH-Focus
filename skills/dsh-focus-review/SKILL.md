# 先核对需求，再检查实现

在当前会话完成检查，不自动创建子代理，不声称自己做了独立审查。

1. 先对照最新用户要求与这次实际改动：必要功能是否完整、错误和空状态是否处理、是否出现无关扩展。已有上下文足够就直接使用；有版本记录时查看相关差异，没有仓库时直接读相关文件，不为检查初始化仓库。
2. 再检查实现正确性：沿真实入口跟到结果，关注本次修改涉及的数据校验、状态更新、重复操作、取消和异步处理。依据实际改动取舍，不把每次检查扩大为全面审计或风格重写。
3. 只报告有依据且可行动的问题，说明位置、触发条件和影响。区分必须修复的问题与个人偏好；收到别人的建议时先核对当前代码，不盲从，也不为了证明自己正确忽略证据。
4. 本次需求中的必要问题直接修复，只补受影响的检查。无关建议不擅自实施。修复后核对相关变化，问题解决就结束，不循环组织多轮全面审查。
5. 检查结果应简短：必要问题及处理结果、仍未解决的限制。未发现问题时说明本次检查范围，不声称绝对正确。随后加载「交付核对」（`dsh-focus-delivery`）；已加载则沿用。
