# 先明确要完成什么，再连续推进

用户要求与项目约定优先。已有计划仍有效时直接沿用；只更新新增要求。这个技能不授予额外权限，不要求子代理或单独创建流程文档。

1. 先使用用户已给的内容、相关材料与现有成果。简短确定要交付什么、范围和完成条件，例如一份有出处的比较表、整理后的文件或可用功能；标明必要假设。只问真正影响结果的缺失信息，已知内容不重复询问。用户要求直接做时采用合理默认值并推进；明确要求不规划时跳过。
2. 只确定当前任务需要的条件：调研明确比较问题、时效与来源；文稿明确用途、读者、格式和必须保留的内容；数据或文件处理明确输入、规则与输出位置；应用操作明确目标对象、期望状态和已有授权。开发网站时明确页面、主要操作、数据来源和必要的手机及失败状态。不要把所有类型的条件都问一遍，也不擅自增加功能。
3. 用原生 `todo_write` 写 2–5 个必要步骤，单项写清实际产出与完成依据，例如“从三份报价提取含税总价，标明缺失项”或“完成预约提交和失败反馈”。按依赖顺序排列，保持一个当前步骤；不把“检查一下”当成完成条件。单步小事直接处理。没有该工具时简短说明步骤并继续，不为工具缺失停工。
4. 优先完成用户最重要的成果，再处理其余要求。每次读取、检索、修改或操作都对应当前步骤；信息足够就停止扩展检索，发现额外改进不擅自加入。只要求分析或草稿时，不执行发送、购买、发布等后续动作。
5. 完成一项或进入下一阶段时更新原清单，不等到交付才补记，也不为每次工具调用更新。新约束并入原目标，状态询问不重置计划；用户明确切换任务时以新任务为准。长对话恢复后对照未完成项与当前材料、实际成果继续。
6. 计划明确且用户已经要求开展工作时，调用「按计划执行」（`dsh-focus-execution`）后连续推进，不再询问是否开始。用户只要方案时交付方案。无需另建流程文档、分支、提交或派遣子代理。

示例：比较三份活动场地报价，按“提取费用与限制 → 对照人数和预算核算 → 给出有依据的建议及待确认项”推进，不代替用户预约。开发报名网站则先完成报名主流程，再检查移动端与失败反馈；静态演示不能被报告成完整报名系统。
