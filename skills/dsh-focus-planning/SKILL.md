# 先明确要完成什么，再连续推进

用户要求与项目约定优先。已有计划仍有效时直接沿用；只更新新增要求。这个技能不授予额外权限，不要求子代理或单独创建流程文档。

1. 先读取用户已给的内容和相关现有实现。用简短说明确定目标、范围和完成条件；把自己的假设标明。只有存在影响结果的重要取舍时，比较可行方案并说明选择理由。只问真正影响实现的缺失信息，已知内容不重复询问。用户要求直接做时采用合理默认值并推进；明确要求不规划时跳过本流程。
2. 对网站，先确定需要哪些页面或区域、主要用户操作、数据来源及前后端边界，顺带明确手机布局和必要的加载、空白、失败状态。按实际需求取舍；不擅自增加登录、支付、管理后台。演示数据和实际功能分别说明。
3. 用原生 `todo_write` 写 3–6 个具体步骤，单项写清实际产出、涉及的已有模块和必要验收，例如“在预约表单中完成提交，覆盖成功和失败反馈”。按依赖顺序排列，保持一个当前步骤；不要把“检查一下”当成完成条件。只有一个简单步骤时直接处理。没有该工具时在对话中给出简短步骤并继续，不为了工具缺失停工。
4. 先完成用户最重要的一条完整使用路径，再完成其余要求。每次读取、修改、检查都应能说明服务于哪个当前步骤；发现额外改进时不擅自扩展范围。
5. 完成一项或准备进入下一阶段时，先更新原清单：如实标记已完成项，把当前实际推进的项设为进行中，再继续行动。不等到交付才批量补记，也不为每次工具调用更新。需求变化时保留有效工作；状态询问和小幅补充不重置整个计划，用户明确切换任务时以新任务为准。长对话恢复后先对照未完成项与当前源码，再接着做。
6. 计划明确且用户已经要求实现时，调用「按计划实施」（`dsh-focus-execution`）后连续执行，不再询问是否开始。用户只要方案时交付方案即可。无需为了本技能另建方案文件、创建分支、提交或派遣子代理。

示例：用户要求做活动报名网站。先确定活动介绍、报名字段、提交去向和成功反馈；按“梳理页面与数据 → 完成报名主流程 → 补齐移动端与失败反馈 → 验证并交付”推进。无法实际提交的静态页面不能被报告成完整报名系统。
